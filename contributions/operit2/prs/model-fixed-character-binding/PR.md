## 问题与复现

角色设为固定聊天模型后，普通发送和附件能力判断仍可能采用全局聊天模型；重新生成又走不同的解析路径。两家供应商提供相同模型 ID 时，角色仅保存 model ID 也无法保留用户实际选择的供应商。

复现：建立供应商 A/B，各添加同名模型；将角色固定到 A 的模型，将全局聊天绑定改到 B，分别发送普通文本、附件并重新生成，检查实际选中的供应商。

## 原因与修复过程

角色持久化与导入/导出只保存模型名，普通请求没有使用角色固定绑定。增加可选 `chatProviderId`，在角色编辑、复制、CLI 编辑及备份中保留供应商/模型组合；通过现有 runtime support 解析这组身份。普通 CHAT 请求、重新生成和附件能力采用同一选择；显式请求覆盖及非 CHAT 功能保持原逻辑。

旧卡片没有新字段时继续允许唯一模型匹配；多个供应商存在同名模型时提示重新选择，避免任意路由。Operit1 原有导入路径仍使用空 provider 的兼容回退，没有引入增强版的额外导入体系。
