## 问题与复现

为普通单人聊天所用的模型启用已有的自动摘要选项，并配置可用的摘要模型。发送足够多轮消息，使消息数达到摘要阈值，或使上下文用量达到 token 阈值；等待回复及本轮工具调用结束。普通发送流程不会触发自动摘要，后续请求继续携带增长的历史。角色群聊已有独立的摘要检查，因此两条路径行为不一致。

## 原因

基线 `AIMessageManager::shouldGenerateSummary` 只有群聊路径调用。`launchAsyncSummaryForSend` 没有调用点；普通发送 worker 在回复落库后直接完成回合，没有检查模型已有的 `enableSummary` 和阈值配置。

## 修复

- 在普通、持久化、成功完成且没有路由迁移的发送回合落库后，使用本次请求解析的模型配置和上下文窗口检查已有摘要阈值。
- 通过已有四参数 `summarizeMemory` 生成并插入摘要，然后以同一角色、模型与工作区上下文重新估算并保存窗口大小；摘要失败时保留完整回复和原历史，并继续结束回合。
- 摘要完成前保持回合忙碌，避免队列提前启动下一轮。摘要请求使用独立 provider service；取消或替换回合后放弃旧结果，并取消该摘要请求。
- 在共享的 `activeTurnId` 基础上增加短提交锁，使新回合、取消和摘要持久化的所有权检查一致。provider 请求和异步窗口计算期间不持有提交锁。
- 普通编辑、删除聊天/消息及响应版本修改入口会在写入前，使当前回合的自动摘要永久失效。即使摘要随后才读取历史，也不能提交该回合的旧快照；回复本身仍正常结束，新回合可以再次触发摘要。

## 影响范围

修改 `MessageProcessingDelegate.rs`，并在 `ChatServiceCore.rs` 的直接编辑、删除及响应版本入口增加摘要失效标记。沿用现有自动摘要开关、阈值、摘要模型和上下文长度计算，不增加模型字段、生成 API 或设置项。群聊仍由原来的协调器负责摘要；非持久化回合、失败回合与路由迁移不进入此分支。
